## Confirmed useful contract properties

* The v1 provider capability and four required verbs remain present with their exact existing values. Apply-v2 and Start-v2 have separate feature blocks and explicit request opt-in. Old Go ignores additive feature keys; its v1 scope/equivalence gate must remain unchanged. These are unshipped fixture advertisements, not installed-host evidence.
* All four preview examples keep saved equal to current and report neither persistence nor start. Selected model plus concrete effort, explicit provider default plus null effort, omission, and inherited-null provider override are distinguishable. An explicitly selected model remains agent-sourced even if the catalog labels that model a default. Provider-default null values are not resolved runtime choices.
* All example command IDs, epochs and exact agent echoes match their requests. The inherited no-op preserves its null override. Persisted Apply and next-wake readiness are separate; already-selected persistence is documented as durable confirmation, not proof of a new write or start.
* The successful selected Apply supplies a fresh wake token different from the selection-preview token; the default Apply does so too. A client must use nextWake.expectedState for Start, not reuse the earlier Apply precondition. An opaque token is required even when expectedNextWake contains unknown defaults.
* The replay example is byte-structure identical to the original start request/response. Start distinguishes immutable PTY-created provider selection, same-created-runtime observation, immediate exit, post-create failure and native/application session namespaces. Neither provider handshake nor actual model/effort is claimed. Model/effort/session IDs remain explicitly unknown in the sample.

## Concrete Go integration findings / clarifications

1. **Receipt placement requires explicit transport work before v2 use.** Completed examples put the contract under `body.result.contract`; stale/unsupported/pre-create/post-create error examples put it at `body.contract`. `alreadyRunning` has no contract at all. Current Go `AnnexCommandReceipt` retains result/error but has no top-level contract field. The current transport correctly preserves HTTP409+status failed as a partial-effect receipt, and the v1 provider flow keeps an uncertainty lock; nevertheless it would discard the v2 post-create observation. Future v2 needs a typed, validated error-contract path (including optional absence), not reuse of the successful-result decoder. Define optional refusal-contract semantics or provide a consistent envelope. Missing contract must remain unknown, not evidence that nothing started.
2. **Clarify running-state scope on early refusals.** Stale/catalog-stale/refused-before-create examples use `running.state:not_running` with unknown evidence and no observed creation. If this is only about a runtime created by this command, document that scope explicitly. It must not be displayed as evidence that the agent has no other runtime; `alreadyRunning` demonstrates that another runtime can instead cause refusal without a contract. Use an unknown observation if absence has not actually been checked. This is a fixture/schema ambiguity, not a finding that desktop production observation is wrong.
3. **Compatibility needs a complete v1-on-new-host pair.** The oldHost example is only a capability fragment/client expectation. The complete 18 transactions all opt into v2. Add ordinary v1 preview/change/strict-start requests against the new host, plus v2-unsupported and malformed-field responses, to prove v1 required fields/scopes remain unchanged and no silent downgrade occurs. V2 managed-composition responses are intentionally outside current Go permitsSave; do not broaden that old equality check to integrate them. The separate capability predicates should specify all supported promise/enumeration values, not version alone.
4. **Important documented states lack Go-facing fixture coverage.** Add saved-but-nextWake-blocked/unverified after successful Apply; stale Apply (not only stale Start); same-provider model change requiring context review; expired/fallback/unavailable catalog; explicit-default generation drift despite equal nullable values; epoch loss and same-ID/different-payload replay conflict. Chat/wrapper/skills/unsupported-layout and authority refusals also need complete envelopes/codes for actionable Go states. Separate backend suites may prove behavior, but these are needed to write conservative client decoding/state tests. The existing replay fixture alone does not prove runtime creation count.
5. **Keep tri-state encoding and identity checks explicit.** Swift effort omission, null and concrete strings need separate cases; an Optional encoded with encodeIfPresent cannot represent clear. Model is tagged, not a bare id/default string. A future client must validate envelope epoch/command, target agent, contract version, normalized selection, effective and stored provider override, source/value choices, result persistence/start semantics and exact wake snapshot/token. Unknown/null session or model/effort stays unknown; PTY-selected provider never becomes a native handshake claim.
