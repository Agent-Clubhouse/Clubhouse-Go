# Actor deinitialization on older iOS runtimes (#218)

The app's minimum deployment target remains iOS 26.0. Debug and Release use default MainActor isolation. With local Xcode 26.0.1 / Swift 6.2, compiler SIL proves that this setting synthesizes isolated deinits even for an explicitly `@MainActor` class whose source contains no deinit. Without the setting, the same explicit class has an ordinary deinit. Changing the setting app-wide would change other inferred actor isolation; this patch preserves it.

A standalone UIKit startup app, without XCTest or Swift Testing, reproduces SIGABRT on iOS 26.0 (23A343): main thread, no current Swift task, a private synchronous Int TaskLocal scope, and release of an implicit-deinit actor class. Its crash reports show malloc pointer-not-allocated → TaskLocal::StopLookupScope → swift_task_deinitOnExecutorImpl. State churn and Go telemetry are not prerequisites. Outside the scope, after the scope, in a Swift task, with an unisolated class, or with explicit empty/nonisolated deinit, the controls complete. `simctl launch` can return zero after this abort; probes require a completion marker instead.

[Swift issue #88036](https://github.com/swiftlang/swift/issues/88036) reports: “This reproduces on iOS 26.2 and older, and appears fixed on iOS 26.4.” That is the reporter's observation, not an Apple release guarantee. [Swift runtime PR #85204](https://github.com/swiftlang/swift/pull/85204) explains: “Item::destroy will call free when there's no task”; its allocation fix merged October 30, 2025. It does not identify an iOS shipping version. Local runtimes are only 18.2 and 26.0; 18.2 cannot run the Go app. Versions 26.1, 26.2, 26.3, 26.4, 26.5 and newer are not locally tested. CI runs an unguarded control and prints its actual runtime/compiler; do not infer a 26.4 boundary from a 26.5 pass.

CI run 41437573191, unit job 125261892396, observes **iOS 26.5 (23F77), Swift 6.3.2 (swiftlang-6.3.2.1.108)**. All eight standalone modes complete with pass/exit markers and no timeouts. The source controls with implicit default-isolated and explicit MainActor classes both pass inside the synchronous task-local scope, with main=true/currentTask=false. Outside completes in 9.465 seconds; inside 4.873, explicit 2.842, and the remaining controls 2.073–2.752. The runtime artifact and unit shard finish successfully. This proves the observed compiler/runtime pair passes these controls; it does not establish which iOS 26.1–26.4 runtime first fixed the bug or safety on real phones. The older 30-second timeout remains unexplained, although the same UIKit/exit path now completes on 26.5.

## Production reachability and limits

The source audit of Go plus pinned Framebriar v0.5.0 finds three `withValue` sites: AnnexTelemetry.measure, AnnexTransport.run, and SDK Telemetry.withSpan. All use async operations, so those scopes execute inside a Swift task. measurePerformance and measureRoutine install no task-local scope. No synchronous app-owned no-task scope was found. Re-audit after SDK adoption.

Five offline production-shaped cycles on 26.0 mounted the actual root, navigated to Dispatcher, applied offline/resync/synchronizing/connected state, returned, recreated root values and tore down the window/store. These ran through DispatchQueue callbacks without XCTest, without adding a scope, and with currentTask=false / AnnexTelemetry.current=nil. Both lazy-only and fixed variants completed. This is synthetic reconnect state, not URLSession/network/device proof. Internal SwiftUI/framework scopes are not exhaustively observable from these public APIs. We have not demonstrated the crashing combination during ordinary production navigation, and cannot prove it is test-only. Forcing a private or Annex scope in the same no-XCTest app reproduces real Queue/Part/Transcript/holder releases before the fix.

Lazy queue ownership removes repeated allocation/discard on SwiftUI root initialization; it does not fix arbitrary class release. The lifetime wrapper itself needed the deinit review. CompanionNavigation on origin/go-dispatcher-tab/first-tab is a value struct: it repeats preference/restoration work but has no actor-class deinit. Preview/demo Store and Preferences construction, SDK preview presenter construction and terminal focus State construction were audited; this patch does not redesign all their ownership. The exact viewport declaration and value helpers extracted from the unmerged reading branch abort in the same no-XCTest scope control; adding only its empty nonisolated deinit makes that control complete. This is declaration-level evidence, not a full reading-branch integration test; After #217 merged, this patch also reviews and protects the actual Bookmark, Viewport and TimelineProjection classes; both hosted and no-XCTest scope probes include populated reading holders.

## Field affinity decisions

An empty nonisolated deinit can release fields on the thread performing the last release. It is not a universal workaround. UI owners and unknown callback/protocol owners retain compiler-generated isolated teardown so their fields still release on MainActor. This leaves those runtime paths vulnerable to the old allocation bug if the missing production combination occurs.

`arc_only` means the current stored fields and concrete constructor captures were reviewed. Queue's production commit captures only Store, whose concrete service/persistence graph is also reviewed as UI-free. The generic lifetime wrapper is approved only at the reviewed constructor sites; it must not acquire raw UI values or UI-capturing factories. The app-owned Runtime factory is reviewed: it captures only the test-mode Bool, runs install-reset before constructing Runtime, and stays lazy in preview/probe modes. Its owner is ClubhouseGoApp State, passed by reference into scene roots; roots no longer construct lifetime holders. The cached Runtime keeps isolated teardown for its UIKit fields. CompanionSceneTestSupport exposes only a weak test reference to the holder; its optional pump callback is DEBUG-only and cleared by the hosted test. Weak references in terminal focus do not own or release the UIKit view. None of these deinits invokes actor-isolated APIs, persists data or cancels work.

## Enforcement and validation

scripts/check-isolated-deinits.py checks the Debug binary's demangled isolated-deinit symbols against scripts/isolated-deinit-policy.json. A new synthesized isolated deinit requires classification. ARC-only entries must lose the thunk; main-actor/generated entries must retain it. At main a8c1964, the policy contains 24 ARC-only protections and 12 retained isolated paths (11 main-actor plus one generated); the latter remain unprotected on an affected runtime if the triggering scope/release combination occurs. SDK adoption removed Go's EnrollmentShakeReceiver; icon-store work added an ARC-only image wrapper. Regenerate counts from the policy at each candidate head, as shown in [the release checklist](testflight.md#next-beta--release-notes-draft).

Ownership review records contain readable SwiftParser-derived surfaces, not whole-file hashes. For ARC-only classes they cover instance stored-property names/types, weak/unowned storage, storage wrappers/macros, inherited types, and nested value storage. Computed properties, property-observer bodies, methods, static caches and literal defaults are excluded. Comments and formatting are trivia and are ignored. The 12 retained-isolation classes have no field fingerprint. The parser ships with Xcode; it requires no downloaded package.

Only the named Queue/lifetime/Store constructor expressions and LiveService's three callback assignments have capture-site records, including visible producer bindings (so changing `service` to a different implementation under the same name is visible). Changes inside one of these expressions conservatively require reviewing that site, including implicit captures; unrelated surrounding methods do not. The policy stores the inputs directly so a review shows which field or site changed, rather than an opaque digest. This is a review gate, not a Swift ownership theorem. No command automatically refreshes ownership approvals. Read-only `python3 scripts/deinit_surface.py --class CompanionStore` and `--captures Annex/Annex/Companion/Views/CompanionAppRoot.swift` show the relevant inputs for review. Focused tests cover method/trivia invariance, field/type/weak-storage changes, conditional storage, new sites and changed captures/producers; the negative binary control still rejects the lazy-only unfixed app.

The runtime-control script attempts the unfixed implicit class release without an OS skip. CI runs this observation after tests and their results upload, with `continue-on-error` and a six-minute step cap. The observer has a 270-second overall budget and a 120-second per-launch limit; remaining modes are explicitly `not_run` if the budget expires. It exits zero regardless of observed outcomes. Setup and per-mode logs are opened before commands start; partial output and `summary.json` upload separately, including on timeout or setup failure. A timeout stays `timeout` even if the app printed completion before its console/exit stalled. A zero simctl status without a completion marker is `incomplete`, not proof of a pass or crash. Launch/exit markers and timeout-only probe process samples distinguish phases where available. Local 26.0 aborts the diagnostic `inside` and `explicit` controls; positive nonisolated controls and the actual fixed Go-type regression pass. The hosted regression dispatches to a no-current-task main callback and releases the actual types under both a private Int scope and AnnexTelemetry scope, with no OS guard.

The first CI observation (run 41419729147, job 125217566625) identified iOS 26.5 and Swift 6.3.2, then its first `outside` launch exceeded the old 30-second limit. The old runner discarded partial output on TimeoutExpired and wrote no mode log, so this supplies no runtime pass/crash result and cannot distinguish a cold launch delay from a stuck console/exit. Bootstatus itself took about three minutes, which suggests a slow environment but does not establish the launch timeout's cause. The probe retains its original UIApplication startup and `exit(0)` path so the next observation can identify where it stops.

The first hosted batch after protecting 17 classes still aborted in CompanionStore while SwiftUI released a prior avatar fixture. That failure prompted the concrete Store/LiveService ownership audit and two additional ARC-only protections rather than a retry-only claim. After the #213 rebase (55f7446), the final hosted batch passed 25 tests repeated three times (75 passing executions), with two pre-existing optional profiling skips. The new deinit tests have no skip or version guard. Package tests passed (962 in 115 suites), coverage ratchet passed (Transport 96.56%, Domain 94.12%), Debug and Release built, and the unchanged vendored SDK passed 66 tests and its 26-file hash check. All eight selected UI tests passed on this base: tree/relaunch, LongReply, preview navigation/content dismissal and all terminal tests. Five ownership-surface tests and negative binary/new-class controls pass. Final-head CI remains required.

The DEBUG-only --deinit-probe route supports offline `cycles`, `queue`, `part`, `expansion`, `holder` and `reading` modes, with optional --deinit-private-scope / --deinit-annex-scope. It prints context and exits; it never constructs a feedback client, pairs, contacts a desktop or sends a report. Use only in a disposable simulator. Normal production launch does not select it, and it is excluded from Release.
